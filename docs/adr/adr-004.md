# ADR-004: Outbox Pattern for Guaranteed Event Delivery, with SKIP LOCKED Polling

## Status
Accepted (revised from initial blueprint)

## Context
Every handler that changes domain state also needs to publish an integration event. Saving to Postgres and publishing to Kafka are two separate systems; a crash between the two leaves state saved with no event published (a silently lost event), or, less likely but possible with certain designs, an event published for a write that never committed.

A further complication specific to this system: `order-capture` and `order-orchestrator` both write to and must poll the same `order_outboxes` table, since both produce integration events for the order context (`order-capture` writes `order.created`/`inventory.commands.reserve`; `order-orchestrator` writes `order.confirmed`/`order.cancelled`). Two independent pollers against one table risk both claiming and double-publishing the same row.

## Decision
Within a single database transaction, every state-changing handler saves both the domain state change and an outbox record (status `PENDING`). A separate `OutboxProcessor`, run via `@Cron`, polls for pending records and publishes them to Kafka.

To resolve the dual-poller race: `findPending` uses `SELECT ... FOR UPDATE SKIP LOCKED` inside an explicit `QueryRunner` transaction. The read (claim) and the eventual `markPublished`/`markFailed` (release) happen inside the same transaction, per record, so Postgres itself guarantees no two pollers can claim the same row, without requiring either poller to know about the other or coordinate through application code.

## Consequences
- Domain write and outbox write are atomic by construction (same `QueryRunner` transaction), eliminating the dual-write problem entirely.
- `order-capture` and `order-orchestrator` can run as independent, independently-scaled processes against the same outbox table with no coordination logic, no distributed lock, no leader election. Postgres' row-level locking is the only mechanism required.
- Cost: `findPending` now requires an open transaction to have meaning; it can no longer be called outside a `QueryRunner`, which is a stricter contract.
- The outbox processor commits or marks-failed per record inside its polling loop, so a single failed publish does not block or roll back the rest of the batch.
