# ADR-005: Idempotency Keys Scoped Per-Customer, Applied Per-Route Not Globally

## Status
Accepted (revised from initial blueprint)

## Context
Network retries, client retries, and Kafka's at-least-once delivery all mean the same logical operation can arrive more than once. Without deduplication, a retried `POST /orders` creates two orders; a redelivered Kafka message re-executes a reservation.

Two mistakes were identified and corrected during implementation, both worth recording:

1. Registering `IdempotencyInterceptor` globally via `APP_INTERCEPTOR` incorrectly required an `Idempotency-Key` header on read routes (`GET /orders/:id`), which are idempotent by HTTP semantics already and have no mutation to deduplicate.
2. Using the raw client-supplied `Idempotency-Key` header value as the Redis lookup key with no additional scoping meant two different customers who happened to submit the same key string (accidental collision, or a buggy client reusing a static key) would collide, and the second customer would receive the first customer's cached order response.

## Decision
- `IdempotencyInterceptor` is applied per-route via `@UseInterceptors`, only on mutating endpoints (`POST /orders`), never globally.
- The Redis key is scoped as `` `${customerId}:${idempotencyKey}` ``, not the raw header value alone. `customerId` is read from the request body at the interceptor layer (before `ValidationPipe` runs, so the raw, unvalidated body is used defensively). This is a documented interim measure: since Phase 1 has no authentication, `customerId` is not cryptographically verified at this layer, and a malicious client could still forge collisions by supplying a false `customerId`. Full correctness requires deriving the scoping identity from a verified auth context (JWT claim or gateway-injected header) once authentication exists.
- The idempotency key and the saga's `correlationId` are deliberately different values. `correlationId` is always server-generated (via `CommandBase`'s constructor) and never derived from client input, since it flows into Kafka headers, log lines, and idempotency namespacing (`` `${correlationId}:create-order` ``) elsewhere in the system, all of which assume UUID format and freedom from client-chosen collisions. Deduplication of retries is guaranteed structurally: a cache hit on the idempotency key short-circuits before the command bus is ever invoked, so no second `correlationId` is ever generated for the same logical operation.
- The cache write (`store.set`) uses `concatMap`, not `tap`, in the interceptor's RxJS pipeline, so the write is awaited before the response is considered complete, rather than fired-and-forgotten alongside the response.

## Consequences
- `GET` routes never require or are affected by idempotency keys.
- Cross-customer response leakage via key collision is closed for the accidental case; the adversarial case remains an open, documented gap until authentication lands.
- `correlationId` remains a trustworthy, system-generated tracing value throughout every log line and Kafka header, regardless of what a client sends as an idempotency key.
