# ADR-006: Database Per Bounded Context, No Cross-Context Joins

## Status
Accepted

## Context
Order and inventory are separate bounded contexts with separate lifecycles, invariants, and rates of change. A shared database with cross-context foreign keys or joins would let either context's schema changes silently break the other, and would make ADR-002's event-driven boundary meaningless in practice, since a direct SQL join is a hidden synchronous dependency that bypasses events entirely.

## Decision
Each bounded context owns its own Postgres database: `doms_order`, `doms_inventory`, provisioned as separate databases within a single shared Postgres instance for local development (per `docker/postgres/init.sql`), with separate instances assumed for production. No table in one context's database references a table in another's. Apps that share a bounded context's database (`order-capture` and `order-orchestrator` both connect to `doms_order`) do so with independent connections, and only because they both operate on the same aggregate's lifecycle (see ADR-003), not because of general convenience.

## Consequences
- Inventory's schema can change without any coordination with order's schema, and vice versa.
- The only way order and inventory ever exchange information is through Kafka events, enforced structurally, not by convention, since there is no database-level path between them.
- Reporting or analytics queries that need data from multiple contexts (deferred to Phase 7's BI streaming) must be built from the event stream or a downstream data warehouse, never from a live cross-context join.
- Local development runs both databases on one Postgres container for simplicity; this is a deployment convenience only and does not relax the schema isolation, since credentials and migrations remain fully separate per context.
